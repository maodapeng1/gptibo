# 私域收款、套餐卡密与游客充值设计

状态：待实现的目标设计，不代表当前生产能力。日期：2026-10-19。
适用仓库：maodapeng1/gptibo（卡网）与 AAUSC/ai-recharge-web（充值执行）。

## 1. 首期边界

保留两个系统。卡网负责套餐、卡密、私域收款登记、游客授权、销售订单和售后；充值系统负责 Session 检测、YIKA 开卡、小玩家订阅和执行记录。

首期一枚套餐权益码兑换一次 GPT Plus 充值，使用既有服务端套餐/地区映射。游客无需注册，不依赖邮件或在线支付网关。充值系统的商户积分、小玩家费用和 YIKA 资金继续作为内部成本独立核算。

卡密先生成、收款后激活、客户确认账号后绑定订单。验证卡密或检测账号不会消耗卡密、开卡或办理订阅。代码数量和已收款额度由后台管理，不允许客户自报已付款后获得执行权限。

暂不包含通用余额充值、游客兑换积分、代理分销、多次使用码、差价升级和赠送码。赠送权益将来需要独立的授权来源，不能伪造现金到账记录或用 1 分钱订单绕过现有正金额约束。

## 2. 用户与运营流程

### 运营端

1. 配置 Plus 权益模板：套餐、可用地区、面值说明、有效期规则、售后说明和启停状态。
2. 批量生成未激活卡密；只增加库存，不产生收入或充值任务。
3. 客户在私域付款，运营人员核对自己实际收款账户的到账记录。
4. 在后台登记渠道、实收金额、币种、交易流水和备注，选择库存码并确认售出激活。
5. 系统原子保存收款分配、销售订单、权益快照和卡密激活记录。
6. 运营人员手动发送卡密、兑换页地址和使用说明；系统首期不自动发送私域消息。

### 游客端

1. 进入 `https://shop.aichongzhi.best/redeem`，输入卡密。
2. 校验卡密后显示套餐、可兑换数量（首期为 1）、有效期与说明；不展示收款人资料、其他订单或内部成本。
3. 点击“检测充值账号”，跳转充值系统的专属检测页。地址仅携带短时一次性票据，Session 不放 URL、不经过卡网后端。
4. 粘贴完整 Session，系统通过商户配置的动态代理检测邮箱、套餐和账号状态。
5. 展示目标账号与本次权益；客户点击“确认使用卡密充值”。修改 Session 或检测过期必须重新检测。
6. 原子绑定卡密、销售订单、目标账号及游客访问权限，创建固定的兑换操作编号。
7. 充值系统按原编号开卡、办理订阅；页面及卡网订单同步展示执行进度。
8. 页面提示保存订单号、浏览器访问权限和单独的订单找回口令；成功后权益标为已使用。

收到卡密说明客户已经在私域完成付款，游客页面不再要求支付第二次。

## 4. 收款、权益和执行状态分开维护

### 收款与退款

- `unpaid`：未确认实际到账，卡密不可激活。
- `paid`：管理员核实并登记实际到账，保留收款来源 `manual`、操作人和时间。
- `refund_pending`：售后审核中或待人工实际退款。
- `partially_refunded` / `refunded`：实际退款已确认并登记对应流水。

销售订单的付款状态只能由已授权管理员登记实际到账或真实支付回执改变。客户截图、“我已付款”或卡密预览均不改变付款状态。

### 卡密

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `inactive` | 未售出、未激活库存 | 激活售出、停用 |
| `active` | 已收款激活，未绑定充值 | 检测账号、确认兑换、受控作废 |
| `locked` | 已绑定唯一兑换，执行中 | 查原订单、原任务恢复、人工核对 |
| `review_required` | 执行失败或结果待人工核实 | 查单、受控恢复或售后；不接受新兑换 |
| `redeemed` | 已明确充值成功 | 查询原结果、售后 |
| `revoked` | 已作废、替换或退款撤销 | 仅查审计记录 |
| `expired` | 已过未使用期限 | 售后核对；不能新建兑换 |

有效期只限制首次使用，不能中断已经锁定的执行、查询或售后。建议从售出激活时开始计时，期限由模板配置。批量生成日期不自动消耗客户有效期。

### 充值执行

沿用 `awaiting_session → issuing → opening → card_issued → submitting → pending → succeeded`。
`unknown`、`payment_blocked`、`action_required` 都保留原卡、原任务和锁定权益；`failed_safe` 代表某一执行阶段明确失败，不代表卡台成本已退回或客户现金已退回。

用户看到的是实际确认的进度，未知结果不展示成成功，也不因超时自动允许换码、换账号或再次开卡。

## 5. 订单和数据归属

首期每枚售出卡密对应一笔单权益销售订单；一次兑换对应该销售订单的一条根兑换记录。多次技术重试均挂在原兑换记录下，不能生成第二笔客户购买或重新消耗卡密。

建议关系：

```text
私域收款记录 ── 收款分配 ── 销售订单 ── 卡密权益
                                  │          │
                                  └── 根兑换记录 ── 充值订单 ── 执行尝试/供应商任务
                                           │
                                    游客访问授权与找回凭证
```

批量生成库存不等于批量售出。首期后台一次售出一枚码；数据层预留一笔收款分配给多笔单权益销售订单，方便以后一次付款购买多枚。分配金额之和不能超过真实到账金额；同一流水必须唯一登记，不得按多个独立全额收款重复记账。

建议追加的数据：

| 表/记录 | 关键字段与约束 |
|---|---|
| `voucher_templates` | 套餐、地区规则、有效期、说明、模板版本、启停 |
| `voucher_batches` | 模板版本、数量、创建人、用途和创建时间 |
| `vouchers` | 随机 ID、批次、`code_hash UNIQUE`、掩码、状态、销售订单、有效期、版本 |
| `offline_receipts` | 渠道、收款账户标识、流水、实收金额、币种、确认人和时间；账户＋渠道＋流水唯一 |
| `receipt_allocations` | 收款记录、销售订单、分配金额；销售订单唯一分配，事务检查分配总额 |
| `voucher_redemptions` | `voucher_id UNIQUE`、销售订单、账号摘要、兑换操作 UUID、当前状态、版本 |
| `voucher_events` | 激活、绑定、恢复、停用、替换、退款等不可覆盖的审计事件 |
| `voucher_preview_contexts` | 仅检测授权、游客浏览器归属、短有效期、预检引用、确认状态 |
| `order_guest_access` | 销售订单、游客浏览器摘要、授权来源、独立找回口令摘要及撤销信息 |
| `fulfillment_outbox` | 操作 UUID 唯一、固定请求快照、重试次数、租约、下次重试时间、受理结果 |

原 `orders` 保存销售状态，`fulfillment_orders` 保存本地执行快照，`live_orders` 保存充值执行。Session 和账号令牌只在充值系统按必要期限加密保存。销售订单不必强制填邮箱，也不使用虚构邮箱占位。

游客访问新增授权需要落实到订单详情和列表查询，不能仅在前端隐藏按钮。下单联系邮箱、充值目标邮箱和登录身份是三个不同概念；不能凭 Session 中的目标邮箱归并用户或授予订单权限。

## 6. 兑换的事务边界

### 校验和检测

- 查询卡密只创建短时浏览器上下文，不锁定消费权益。
- 充值系统获得 `precheck_only` 授权，只能检测此权益允许的账号；不能使用普通已付款交付票据提前执行。
- Session 检测完成产生短时服务端预检引用，绑定上下文、账号摘要、Session 摘要、套餐地区及有效期。
- 卡网通过内部签名请求核实引用，浏览器自报“检测成功”或账号 ID 无效。

### 客户确认兑换

在卡网同一数据库事务内：

1. 锁定预览上下文、卡密、对应销售订单和收款分配。
2. 校验已激活、未过期、未退款/售后冻结，金额及权益快照有效，预检未过期且为同一账号。
3. 如果已有根兑换记录，返回原订单；不能创建第二笔，也不能把另一位游客加入原订单。
4. 将卡密绑定到根兑换及目标账号，状态改为 `locked`。
5. 创建本次游客的原订单访问授权、独立找回凭证，以及执行 outbox；写审计事件。
6. 提交事务。事务提交后才允许向外部服务发执行请求。

同一个码的并发确认只能有一个获胜者。其他浏览器仅得到“卡密已绑定，请通过原订单查询”，不获得原订单详情。只有原授权浏览器的幂等重试才返回自己的原订单。

### 跨系统执行

Worker 以固定兑换 UUID 发送执行指令。充值系统用唯一来源订单/兑换 UUID 落库，保存确认过的请求指纹；重复消息返回同一任务，参数不一致拒绝。

执行前卡网再次验证“有效收款＋该权益已锁定给该兑换＋未被售后撤销”。现有只检查已付款的 `Eligible/Authorize` 需要增加卡密来源条件，避免预览票据绕过兑换锁。

充值系统从自己的预检引用读取 Session，不将其回传卡网。既有开卡键 `UUID:open` 和订阅操作 UUID 在同一次执行尝试中保持不变。跨系统 HTTP 超时后查询原编号；不能新建 UUID 试图解决未知结果。

outbox、内部请求防重放和任务幂等分别处理消息可重投、签名重放及实际操作去重。任务允许重复投递，不代表允许重复开卡。

## 7. 游客查单和换设备

- 首次兑换由当前浏览器保存 HttpOnly 订单访问 Cookie；订单号用于定位，不是授权凭据。
- 根兑换建立后，向客户提供独立的高强度找回口令，可复制/下载保存；服务端仅存摘要。
- 另一个设备需要“订单号＋找回口令”才可兑换短时订单访问会话。成功和失败尝试均限流，口令不进入日志或 URL query。
- 卡密使用后不再作为查单登录凭据：知道卡密的人不应因此获得已绑定客户的账号和订单详情。
- 丢失口令时，由私域客服核实购买记录后，在后台重发短时恢复票据并审计；可撤销原恢复凭据。不能仅凭公开订单号或一句“这是我的码”重发。
- 一次性浏览器交付票据继续五分钟有效；失效后从已有订单授权重新签发，不让客户重新消耗卡密。
- 不依赖邮箱；以后注册用户可以在充分验证后显式认领已有订单，不能依据未验证邮箱自动绑定。

## 8. 异常与售后规则

| 情况 | 权益处理 | 后续动作 |
|---|---|---|
| 码无效/未激活/过期 | 不绑定、不执行 | 提示核对或联系发码方 |
| Session 无效/代理失败/账号停用 | 保持 `active` | 修正或重检，不开卡 |
| 两人同时确认同一码 | 只锁定给一个根兑换 | 另一位无权读取原订单 |
| 余额不足且没有产生外部操作 | 保留原兑换并提示商户处理 | 补足商户额度后受控恢复；不假称客户余额不足 |
| 开卡结果未知/网络超时 | `locked` 或 `review_required` | 用原编号核对；不解锁重开 |
| 开卡明确未受理，且确认无成本/未支付 | 人工审核可恢复权益 | 优先恢复原订单；需要新尝试时保存新的尝试号与证据 |
| 已开卡但订阅失败 | `review_required` | 核对余额、卡费及支付结果，优先原卡恢复，不自动重新开卡 |
| 需要银行验证 | 保持锁定 | 在原任务完成验证或人工处理 |
| 充值成功但回调/同步丢失 | 保持原兑换 | Worker 拉取最终结果；成功落库后标记 `redeemed` |
| 客户重复刷新或关页 | 状态不重置 | 自动查原订单、原任务 |
| 退款申请发生在执行前 | 冻结权益并阻止执行 | 核实没有外部操作后实际退款 |
| 执行中要求退款 | 保持执行锁 | 先核对卡台和订阅结果，不能直接退款又继续充值 |
| 客户实际收到私域退款 | 撤销对应权益并登记退款流水 | 已消费权益的售后保留历史，不重开原码 |

恢复权益不是简单把 `locked` 改回 `active`。必须先有可审计的“旧尝试已终止且不会再成功”证据，并禁止旧执行授权和消息继续生效；确认不清楚时保持人工核对。

补发优先生成新码、撤销旧的未使用权益，并关联旧销售订单，不能同时保留两份可用权益。已开始执行的旧码须先解决在途任务后才能补发。

## 9. 后台权限和安全

- 首期需要不依赖邮件的安全管理员登录，建议管理员账号密码＋TOTP；不开放游客创建管理员。
- 后台能力拆为：生成库存、确认收款并激活、核查订单、恢复执行、停用/补发、登记退款。首期可由同一管理员操作，但事件分别记录。
- 收款激活、恢复执行、补发和退款都要求处理说明及版本校验；确认弹窗显示影响的订单、卡密和金额。
- 卡密采用密码学随机生成，建议 `AI-` 前缀＋32 位 Base32 字符分组显示；不使用递增编号或手机号。
- 规范化只处理约定的大小写和分隔符。服务端保存带独立服务端密钥的摘要及掩码，用版本字段支持密钥轮换；不记录明文码到请求日志。
- 首期完整卡密只在生成/安全导出时显示一次；后台日常仅展示掩码。遗失未发出的码可按审计流程撤销并重新生成。
- 游客验证与找回按可信入口 IP、浏览器和摘要限流；错误不泄漏其他客户资料。
- Session 不进入卡密导出、客服备注、卡网数据库或分析日志；PAN/CVV 不持久化到订单。
- 用户提交确认只能授权当前权益及已检测账号，不能选择内部商户账号、请求价格、供应商 Key 或任意套餐。

## 10. 接口草案

路径为设计草案，实施时同步路由契约与权限测试。

| 接口 | 调用方 | 职责 |
|---|---|---|
| POST `/api/admin/voucher-batches` | 管理员 | 生成未激活库存及一次性导出 |
| POST `/api/admin/voucher-sales` | 收款管理员 | 登记实际收款、创建销售订单、分配并激活卡密 |
| GET `/api/admin/vouchers` | 管理员 | 掩码列表及状态筛选 |
| POST `/api/admin/vouchers/:id/actions` | 有对应权限的管理员 | 停用、受控替换及审计 |
| POST `/api/vouchers/preview` | 游客＋浏览器 CSRF 会话 | 校验码、签发仅检测上下文，不消费权益 |
| POST `/api/fulfillment`，预检动作 | 受限预检 Cookie | 现有检测能力，返回服务端预检引用 |
| POST `/api/internal/voucher-redemptions/confirm` | 充值系统签名请求 | 代表持有合法确认上下文的游客，原子绑定兑换并创建 outbox |
| POST `/api/internal/fulfillment/authorize` | 签名服务请求 | 扩展已有接口：校验根兑换、权益绑定及收款 |
| POST `/api/fulfillment`，执行/查询动作 | 订单授权或签名 Worker | 复用并扩展既有幂等执行与状态查询 |
| POST `/api/orders/recover-by-secret` | 游客＋限流 | 订单号＋独立找回口令换取浏览器授权 |
| GET `/api/orders`、`/api/orders/:id` | 已授权游客 | 新增卡密来源授权的服务端校验 |

新预检上下文与确认动作必须显式区分授权范围。预检 Cookie 不能调用订单执行动作；后台确认 RPC 不能信任浏览器自报的预检资料或任意 buyer ID。

## 11. 与现有代码的衔接

可以复用：游客 buyer Cookie、订单与审计事件、授权票据、HMAC/nonce、执行锁、YIKA/订阅幂等调用、Worker 查询与失败退避、交付页进度。

需要新增：自有卡密表及销售流程、人工到账登记、无邮件管理员登录、预检授权范围、根兑换及 outbox、游客找回口令、销售订单授权扩展和后台卡密管理。

注意：`ai-recharge-web/functions/redemption-provider.ts` 现在是未接通的外部积分兑换占位入口，不能作为自有套餐卡密接口直接上线。卡密放在卡网统一管理，充值系统只接受受限授权，不再平行维护另一套客户卡密库存。

现有 `fulfillment_orders.order_id` 和 `commerce_orders.sales_order_id` 是单订单唯一映射。首期坚持一枚码一笔单权益销售订单以复用此约束；受控重试挂在根兑换下，再显式扩展尝试模型，不能绕过唯一约束新建购买订单。

## 12. 分阶段落地与验收

1. 库存与销售：无邮件管理员登录、模板、批次生成、人工到账登记、激活、撤销、审计。
2. 游客兑换：卡密预览、受限预检、目标账号确认、原子锁定、找回口令、原订单访问。
3. 自动交付：outbox、严格执行授权、原编号幂等、状态回写、终态核销。
4. 异常售后：原卡恢复、核对记录、退款登记、受控补发、旧授权撤销。

必须通过：

- 未激活码不能执行；客户自报付款不能激活。
- 同一收款流水不重复记账，分配金额不超实收；重复激活请求只形成一笔销售。
- 预检不消费卡密、不开卡；Session 修改或超时后旧预检失效。
- 同码并发确认只产生一个根兑换、一个执行授权、一次开卡。
- 非原浏览器拿到已使用卡密不能读取原订单或目标账号。
- 确认提交前后断网、服务重启、重复消息、同步失败均继续同一笔订单。
- 未确认的开卡/订阅结果不能解锁卡密；恢复后的旧消息不得再执行。
- 实际退款与执行互斥；内部积分释放不计为客户现金退款。
- 完整码、Session、供应商密钥和卡片敏感信息不进入卡网日志或导出。

先使用隔离数据库与模拟供应商验证。真实上线需要明确 Plus 售价、有效期、私域收款渠道、管理员资料和商户备付额度；邮件及在线支付接口仍可暂缓。首次真实验收应由运营人员核实真实到账，使用明确授权的账号办理一笔订单，再核对卡台成本、订阅状态和各系统流水。

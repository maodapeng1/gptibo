# 套餐卡密试运营操作说明

首期提供一次 GPT Plus 充值权益。游客无需注册，不依赖邮件验证码或在线支付网关。

入口：

- 客户兑换与查单：`https://shop.aichongzhi.best/redeem`
- 卡密运营后台：`https://shop.aichongzhi.best/voucher-admin`
- 现有管理工作台：`https://shop.aichongzhi.best/admin`，也可在卡密后台登录后访问。

## 管理员首次登录

后台使用账号、密码和 TOTP 动态验证码。初始化资料只保存在私密文件，不打印到部署日志、不提交 Git。
将资料中的 TOTP 密钥加入自己的验证器应用，再用密码及六位动态验证码登录。

服务器显式初始化：

```
VOUCHER_ADMIN_SECRET_DIR=/opt/gptibo-shop/.secrets /opt/gptibo-shop/storefront bootstrap-voucher-admin
```

初始化只生成一次，已有资料不会覆盖。`deploy/commerce/compose.vouchers.yaml` 是独立密码登录的显式配置，生产安装为 `compose.override.yaml`，由默认 compose 命令自动加载。API 挂载密码摘要和 TOTP，Worker 不需要管理员凭据。

必须保留原 AUTH_SECRET、数据库和充值系统加密密钥。AUTH_SECRET 也参与卡密摘要，不可用更换它的方式重置管理员密码。

## 从库存到发码

1. 在后台填写批次名称、数量和售出后有效天数。套餐固定为已配置的 Plus，地区沿用服务端映射。
2. 生成后立即下载完整码。后台日常只保留掩码、批次和状态，无法再次查看原码。
3. 核实自己实际收款账户已经到账，再选择一枚未激活码，选择“确认私域实际到账并激活”。
4. 填写实收人民币金额、微信/支付宝/银行渠道、收款账户标识、真实交易流水、核对说明，并勾选确认。
5. 激活会创建独立销售订单，期限从激活时开始。生成库存不会计收入，也不会开卡。
6. 从已安全保存的库存文件取对应卡密，手动发送给客户，同时发送兑换地址与使用说明。

首期一笔收款激活一枚码；流水重复登记会被拒绝。暂不支持同一笔收款拆分多个码，不能用虚构流水后缀绕过去。完整码遗失且尚未使用时，可审计停用或替换；新码沿用原权益和原有效期，不额外记一笔收入。

建议发给客户：

> 你的 GPT Plus 充值卡密：填写对应卡密。
> 兑换地址：https://shop.aichongzhi.best/redeem
> 先检测账号，确认邮箱和套餐后再开始。检测不会消耗卡密。
> 充值开始后请查询原订单，勿重复购买。兑换后请保存订单找回资料。

## 客户兑换

1. 输入卡密并验证，确认套餐和使用期限。
2. 进入专属账号检测页，粘贴完整 Session。
3. 核对返回的邮箱、当前套餐和账号状态，点击“确认使用卡密并充值”。
4. 卡密绑定到唯一根兑换和已检测账号，后台持续推进原任务。
5. 进度包括账号检测、提交开卡、等待开卡、提交订阅、完成充值；结果未知时保持原任务。
6. 返回兑换页或“我的订单”查看记录。目标账号以脱敏邮箱保存，完整 Session 不经过卡网后端。

卡密本身就是套餐权益，不要求游客再次购买站内积分。充值单的 funding_source=voucher，旧积分订单仍按 wallet 结算。两者都不能替代 YIKA 实际钱包余额、卡片充值资金或小玩家的真实平台额度。

## 查单与找回

当前浏览器可以直接查看自己的订单。确认兑换后，可生成并下载独立订单找回口令。
换设备使用“订单号＋找回口令”，已使用卡密不能作为订单登录凭据。
生成新找回口令会使旧口令失效，请不要随意重复更新。

如果客户丢失口令，先通过私域核实原购买记录和购买人，再在后台选择“核实购买人后重发订单找回口令”。填写核对依据，系统审计并只在本次响应中展示新口令。不要仅凭公开订单号重发。

## 异常处理

开卡幂等键是“充值执行编号”后接 `:open`，不能用销售订单号代替。

后台可查看：实收金额、原收款流水、退款流水、销售订单、充值执行编号、卡台开卡任务、订阅平台任务、脱敏目标邮箱、最近异常代码和追踪号。

- 尚未创建卡台任务：可以请求取消。充值系统以数据库取消标记和插入保护阻止迟到请求重新开卡；已存在执行记录时拒绝此操作。
- 已开卡而支付受阻：补足真实供应商额度或解决原因后，选择“用原卡恢复支付”；不会重新开卡。
- 未知开卡且没有供应商引用：先向卡台核实请求未受理且不会继续执行，再选择受控关单并记录依据。不能仅因等得久就关单。
- 有在途结果或需要银行验证：保留原订单核对，不能新发第二份权益，也不能直接登记退款。
- 未使用权益：可停用；补发会撤销旧码，新码仍关联原销售订单，旧预览授权失效。
- 实际全额退款：先确认没有未知在途任务、执行已经取消或供应商结果明确，再实际退款并登记唯一退款流水。此按钮只记账，不替你转账。

首期不自动重置已执行权益来再次开卡。已开始的异常订单支持原任务恢复、受控关单与核对后退款。内部额度回退不表示客户现金已退回。

## 数据与恢复

卡网增加迁移 `036_voucher_sales.sql`；充值增加 `0011_voucher_prechecks.sql`。
应用迁移后重新执行 grant-runtime。部署前分别备份 PostgreSQL、SQLite、配置和加密密钥。
先升级数据结构和双方代码，再开放新兑换入口；不允许拿旧版付费授权代替卡密确认授权。

核心限制：卡密仅检测时不锁定；确认与原订单授权原子写入；同码并发只允许一个确认；预检票据不能直接执行；确认响应丢失由持久化 dispatch 和原编号补偿；取消与真实执行插入互斥；旧钱包计费保持原规则。

本次回归使用隔离 PostgreSQL、内存 SQLite 和模拟供应商。生产验收不创建虚假到账记录，不自动开卡或支付。真实验收需要你核实一笔实际到账，并使用明确授权的目标账号。
